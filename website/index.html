Project overview

Matching lost items to a fictional catalogue.

Campus Find helps students turn a short item description into up to three possible matches, each shown alongside its original record.

01

The problem and project value

Who it is for

Students trying to find a lost item may remember its colour, shape or a small detail, but not the words used in a found-item listing.

For example, “black water bottle” and “dark insulated flask” may refer to similar objects. Exact keyword overlap can miss that connection.

What the project explores

The project compares a simple keyword baseline with an AI-assisted matching approach. The aim is to make a small candidate list easier to inspect while keeping the source description visible.

The present scope is deliberately limited to synthetic data. Any improvement from AI remains a hypothesis until live-model evaluation is completed.

02

Input → processing → output

  1. 1 / INPUT

    Describe an item

    Enter an English description of up to 300 characters. Optionally select a category. Use fictional details only.

  2. 2 / PROCESSING

    Search and validate

    Check input and request boundaries, load the selected SQL records, and run the chosen search method. Validate AI IDs and source excerpts before display.

  3. 3 / OUTPUT

    Inspect possible matches

    Show up to three ranked records, or a clear no-match, clarification or error message. Original descriptions remain visible.

Keyword search · available

Rank records by shared lowercase words; break ties by item ID. Return at most three records with a positive score. It does not understand synonyms or reject all contradictory details.

AI matching · awaiting configuration

A hosted language model compares item type, colour and distinctive features. Its response must contain valid catalogue IDs and exact evidence excerpts. Unknown IDs, duplicates, excessive results and unsupported evidence are rejected.

Empty or overlong input, obvious ownership/contact requests and very vague descriptions are handled before any model request. Keyword mode never calls the model.

Domain customisation

The prompt focuses on item type, colour and distinctive features. The app limits output to three possible matches, checks every ID against the selected catalogue and disallows ownership decisions.

Data and privacy

Only fictional catalogue records are stored. The app does not persist user queries or profiles. AI mode sends the fictional query and selected records to the configured provider; that provider’s retention policy applies.

AI tools assisted with coding, UI development, synthetic records and draft evaluation cases. Team members are responsible for reviewing the work and explaining the implementation. Independent record and answer-key review is still pending.

Run the app and verify the result

  1. Open Campus Find. No application account is required. A free-hosting cold start can take about a minute.
  2. On Search, choose Keyword search and leave the category as All items.
  3. Enter the example below and select Search items.
  4. Confirm that LF-001 — Black bottle is the first possible match. Read its original description before assessing relevance.

Example inputblack insulated bottle with a silver lid

Expected first resultLF-001 — Black bottle
Black insulated metal water bottle with a silver screw lid and a small crescent sticker.

A successful run shows the search method, no more than three catalogue items and the original descriptions. This example confirms the keyword flow; it does not demonstrate AI performance. Other keyword results may conflict with the query.

Run locally from the private source repository

After receiving repository access, download or clone the code. With Python 3.13 installed, open a terminal in the repository folder and run:

python -m venv .venv
# Windows PowerShell
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe -m streamlit run app.py

Open localhost:8501. On macOS/Linux, use .venv/bin/python in the last two commands. SQLite is created and seeded automatically; no database account is required. If port 8501 is busy, append --server.port=18501.

Activate AI matching when a provider key is available

Copy .env.example to the ignored .env file. Set LLM_API_KEY, LLM_BASE_URL, LLM_MODEL and LLM_PROVIDER, then restart. On Render, use server environment variables.

The adapter requires a compatible Chat Completions JSON endpoint. Provider/model compatibility and retention settings must be checked before use. Never put a key in this HTML page or commit it. Without configuration, AI mode displays an explicit message and produces no AI matches.

Evaluation and limitations

The candidate evaluation set contains 20 synthetic queries. Results below are for the keyword baseline and shared input checks; live AI accuracy has not been measured.

A concrete failure

“purple telescope” has no suitable catalogue item, but keyword search can return the purple notebook or keys because they share “purple”. Colour overlap is not sufficient evidence of a match.

A boundary case

“Who owns this black bottle?” is refused. The application does not disclose an identity or treat a search result as proof of ownership.

Main limitations

  • Only 30 synthetic records and a small, not yet independently reviewed evaluation set.
  • No live-model results yet; there is no evidence that AI outperforms the baseline.
  • Exact excerpts establish source provenance, not semantic correctness.
  • English input checks are safeguards, not a comprehensive personal-data detector.
  • Human evidence review and two-classmate usability checks remain pending.

Engineering checks: 45 automated tests passed in Linux CI, including PostgreSQL integration; the Docker build also passed. Mock provider responses test error handling and validation, not real AI quality. CI evidence is recorded in the project documentation.

Reproduce evaluation
python -m pip install -r requirements-dev.txt
python -m pytest -q
python -m evaluation.run --mode keyword

The runner writes a report with dataset and prompt hashes, a timestamp and each synthetic outcome. Once a key is configured, python -m evaluation.run --mode ai runs the same cases with the model and can incur provider charges. Proposed AI targets include at least 9/10 top-three hits and 4/4 no-match cases; neither is claimed as achieved.
